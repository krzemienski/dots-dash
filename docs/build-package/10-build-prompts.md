# Master and phase execution prompts

These prompts are reusable instructions for an authorized implementation task. They do not supply new authority to create accounts, grant persistent access, contact third parties, incur charges, publish or expose data. Replace only the project/environment references with verified values. Never paste runtime secrets or private source exports into a prompt or repository.

## Master execution prompt

Version 3 execution must also follow the amendment and E0-E6 prompts below, including Python-first migration and permitted session/host boundaries.
Build the private-first work dashboard described in this package. Read README, current-state, product requirements, contracts, security model and verification plan before editing. Inspect the actual repository and current diffs, then identify the first dependency-ready milestone. Prioritize correspondence and schedules. Preserve request-to-action-to-evidence accountability and honest source freshness.

Work on real functionality, not a decorative mock. Keep the private runtime separate from reusable code. Do not import personal records, credentials, private source links, hosting identities or original private Git history into the repository. Start empty; use explicitly authorized controlled functional records in an isolated private test account for end-to-end validation. Existing isolated tests are useful but cannot prove a live integration.

For each milestone, implement coherent code and migrations, run the applicable checks, inspect the signed-in UI where available, and write an evidence report tied to the exact revision. Distinguish local save, delivery, acceptance, execution and verified outcome. Keep unsupported integrations unconfigured. Do not create a second assistant and claim it is the owner's existing dot. Confirm a real supported MCP/delivery route and required owner installation approval before connecting it.

Coordinate independent changes without overwriting other work. Preserve user edits. Make reviewable local commits when authorized. Report exact commit IDs; claim a remote push or deployment only after verifying the same revision there. Do not change repository visibility or license without authorization. When blocked, name the exact missing access, unsupported API, approval or technical failure, continue independent authorized work, and stop the dependent operation. Never replace missing evidence with a fake success state.

At completion report: files and schema changes, functional outcomes, passed/failed/not-run checks, source freshness/coverage, known gaps, security implications, exact revision, and the next dependency-ready milestone. Update current-state documentation to match what was actually established.
